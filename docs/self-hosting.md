# Независимый запуск Unitify

Сверено с исходниками 27 октября 2026 года. Эта инструкция предназначена для
**копии получателя**, а не для изменения сервера автора.
Готовое поручение ИИ-агенту: [agent-handoff.md](agent-handoff.md).

## Что передаётся

Нурали разрешил получателю использовать существующее расширение Unitify Bridge.
Можно использовать его исходники и собрать готовый ZIP для собственного сервера,
не создавая новый item в Chrome Web Store и не проходя новую публикацию в Google.

Это разрешение не передаёт аккаунт разработчика Google, токен Telegram, облачную
базу, личные Moodle-ссылки или доступ к учебным данным автора. Оно не заменяет
условия использования сторонних зависимостей и материалов.

В версии 0.3.2 backend расширения фиксирован. Код из `/extension` нового бота
не сработает в старом пакете, обращающемся к другому серверу. Поэтому независимая
установка состоит из Cloudflare-развёртывания, адаптации закрытого доступа
и установки пакета **того же расширения** с адресом нового сервера.

Использовать неизменённую магазинную установку с любым новым backend пока нельзя:
выбора сервера в интерфейсе нет. Если нужен именно этот вариант, потребуется
доработка расширения и обновление существующего item владельцем; не отдельная
публикация получателем. Факт одобрения/наличия текущей версии в магазине здесь не подтверждается.

## 1. Окружение и изоляция

Работайте в отдельном clone/fork. Не передавайте всю рабочую папку автора:
в ней могут быть локальные секреты, кэш Wrangler и не входящие в репозиторий материалы.

Нужны Node.js с поддержкой `node:sqlite` и `import.meta.dirname`, npm, Python 3,
системная утилита `zip`. На Windows обеспечьте совместимое окружение для сборки.
Проверенная локально конфигурация: Node.js 26.0.0, Python 3.12.6, Wrangler 4.151.0.

```bash
npm ci
npx wrangler --version
```

Не обновляйте зависимости и compatibility date без причины.
Для новых облачных ресурсов используйте собственный Cloudflare-аккаунт и
отдельного Telegram-бота. Проверьте актуальные доступность функций и лимиты тарифа;
бесплатная и неограниченная работа не гарантируется.

## 2. Обязательная адаптация доступа для одного человека

Просто развернуть текущий конфиг недостаточно.

| Место | Текущее ограничение |
|---|---|
| `worker/access.js:privateChatIds` | Ровно два разных положительных ID |
| `worker/access.js:demoAccess` | Зависит от двух владельцев |
| `worker/access.js:retireOtherUsers` | Историческая очистка, проверка владельцев `nurali`/`nurbek`, рассылка и удаление |
| `worker/db.js:activeUsers` | Проверяет ровно двух владельцев |
| `worker/db.js:calendarUsers` | Два SQL-параметра, `LIMIT 2` |
| `worker/cron.js:runCron` | Не работает при количестве владельцев, отличном от двух |
| `worker/lms-extension.js` | Проверка двух ID, два параметра при привязке |
| `tests/private-access.test.mjs`, другие тесты доступа | Закрепляют исходную модель |

Найдите также все вызовы `privateChatIds`, проверки `length !== 2`, `length === 2`
и SQL, завязанный на количество владельцев. Согласованно поддержите одного
настоящего владельца, сохраняя закрытый вход при пустой/невалидной конфигурации.
При необходимости можно поддержать ограниченный список нескольких владельцев,
но не открывайте публичную регистрацию без отдельной задачи.

Не добавляйте фиктивный второй ID. Не выдавайте демодоступ как независимый аккаунт.
В новой установке `BOT_DEMO_ACCESS` по умолчанию не нужен.

Историческую очистку исключите из нового сценария или адаптируйте так, чтобы она
не требовала старых имён и не удаляла данные/не отправляла старое уведомление.
На чистой базе для регистрации не должны требоваться записи автора.
Обновите содержательные тесты доступа, pairing, cron и SQL под выбранную модель.

`REGISTRATION=closed` и `MAX_USERS` не заменяют эти изменения.
Не выполняйте адаптацию непосредственно в production автора.

## 3. Личное расписание

Создайте `public/<slug>/schedule.js` с собственными данными по формату из README.
Проверьте формат баркода в `worker/bot.js`: пустое поле не позволит зарегистрироваться.
Личные исходные профили автора могут иметь пустые баркоды.

Обновите имя, группу, даты триместра и праздники, занятия, сокращения и при
необходимости английские соответствия предметов в `worker/i18n.js`.
Расписание и даты нельзя выдумывать; до получения данных используйте явно
обозначенную заготовку и не считайте персонализацию завершённой.

В публикуемой копии не оставляйте старые личные профили по умолчанию.
Сначала разрешите зависимости `aliasOf`, затем проверьте оставшиеся HTML,
manifests, JSON и изображения. Генераторы не гарантируют удаления устаревших файлов.

`hidden`/`private` не защищают статические URL. Если сам сайт должен требовать
вход, нужна отдельная HTTP-защита с проверкой путей и API; не ограничивайтесь
скрытием карточки с главной и запретом индексации.

## 4. Конфигурация Cloudflare

В `wrangler.jsonc` установите:

- новое имя Worker;
- новый D1 `database_name` и фактический `database_id`;
- `PUBLIC_URL` — свой HTTPS origin без завершающего слеша;
- `ADMIN_CONTACT` — контакт нового владельца;
- `MAX_USERS` — согласно адаптированному доступу;
- `TZ_OFFSET_MIN: "300"` для UTC+5 либо подходящее значение владельца.

Для первого запуска используйте `workers.dev`: удалите маршрут
`s.zhengisbay.com`, включите `workers_dev: true` и узнайте свой workers.dev subdomain.
Домен автора не является общим ресурсом для новых установок.
Собственный домен можно подключить после проверки основного запуска.

Сохраните:

- `main: "worker/index.js"`;
- сборочную команду;
- `assets.directory: "./public"`, binding `ASSETS`;
- обработку `/tg/*`, `/api/lms/*` и служебных путей Worker;
- D1 binding `DB`, `migrations_dir: "migrations"`;
- Durable Object binding `TICKER` с `class_name: "Ticker"`;
- миграцию DO `new_sqlite_classes: ["Ticker"]`;
- резервный cron `* * * * *`;
- rate limits и наблюдаемость.

D1 SQL-миграции и миграция класса Durable Object — разные механизмы.
Отдельную ручную SQL-таблицу вместо Ticker создавать не нужно.

## 5. Аккаунт и новая D1

После удаления старого route и настройки отдельного имени:

```bash
npx wrangler login
npx wrangler whoami
npx wrangler d1 create unitify-personal-db
```

Имя базы — пример. Подставьте выданный UUID в конфиг. Не используйте UUID базы
автора. Не импортируйте старых пользователей, Moodle-записи или `owners`.

Примените **все** миграции:

```bash
npx wrangler d1 migrations apply DB --local
npx wrangler d1 migrations apply DB --remote
```

Два файла имеют префикс `0005`; оба нужны. Проверяйте фактически применённые
файлы и ошибки, не удаляйте один по совпавшему номеру.
`--local` меняет локальную D1, `--remote` — облачную.
В новой базе должны существовать все таблицы/столбцы для пользователей, владельцев,
дедлайнов, сообщений, LMS-привязок, оценок и attendance.

## 6. Сборка и первый деплой

```bash
npm run build
npm test
npx wrangler deploy --dry-run
npm run deploy
```

`npm run build` запускает генерацию HTML, JSON, картинок и ZIP.
`wrangler deploy` также запускает сборку из `build.command`.
На этом этапе отсутствие токена бота не мешает опубликовать сайт, но Telegram
ещё не готов.

Получите фактический HTTPS URL из вывода Wrangler. Согласуйте с ним
`PUBLIC_URL` и адреса расширения из следующего раздела, пересоберите и повторно
опубликуйте окончательный пакет. Если адрес был известен заранее, используйте его сразу.

## 7. Тот же Unitify Bridge без новой публикации Google

Не создавайте новый item в магазине только ради самостоятельного экземпляра.

Согласованно замените origin в:

1. `extension/background.js`: `API = "<свой-origin>/api/lms/"`.
2. `extension/popup.js`: ссылка скачивания обновления.
3. `extension/manifest.json`: серверный `host_permissions` и `homepage_url`.
4. Ссылках политики приватности, шаблонах/генераторах и подсказках.

Поиск по репозиторию:

```bash
rg -n 's\.zhengisbay\.com|nxxschedule_bot|nxxbruh' worker extension tools public README.md docs
```

Проверяйте каждое совпадение по смыслу. В частности,
`tools/build-pages.py` содержит имя старого бота, а генераторы картинок —
подпись старого домена. Не удаляйте авторство сторонних материалов.

Хост Moodle `lms.astanait.edu.kz` остаётся прежним для AITU. Не заменяйте его
вместе с backend. Поддержка другой LMS — отдельная адаптация парсера и правил.

```bash
npm run build
npm run deploy
```

Готовый ZIP: `<свой-origin>/downloads/unitify-moodle-reader.zip`.
В корне архива должен лежать `manifest.json`.

Получатель распаковывает архив в постоянную папку, открывает
`chrome://extensions`, включает режим разработчика и выбирает
«Загрузить распакованное». Далее получает `/extension` в **своём** боте
и вводит код в расширении. Код действует 10 минут.

Не копируйте локальное хранилище, device token и данные расширения автора.
При переносе ранее использовавшейся установки сначала отзовите старую привязку
через исходную установку/бота и используйте новую чистую копию.
Проверьте в DevTools, что pairing и sync идут только на новый backend.

Код распакованного расширения не обновляется из Cloudflare автоматически.
Для обновления заменяют файлы в той же папке, нажимают ↻ в
`chrome://extensions` и перезагружают Moodle. Обычные магазинные обновления
относятся к существующему item и управляются его владельцем.

## 8. Новый Telegram-бот и секреты

Создайте собственного бота через официальный BotFather. Не используйте токен
автора: установка webhook для того же токена перенаправит его действующего бота.

На правильно выбранном Worker интерактивно задайте:

```bash
npx wrangler secret put TELEGRAM_TOKEN
npx wrangler secret put BOT_ALLOWED_CHAT_IDS
```

После адаптации вторая переменная содержит один настоящий числовой ID владельца
или корректный разрешённый список. Не храните значения в документации/Git.
Секреты из `.dev.vars` сами не публикуются. Команды изменения секретов могут
сразу публиковать новую версию Worker — учитывайте выбранное имя/окружение.

Получите Telegram ID до регистрации. Существующая команда `/id` находится
за проверками доступа/регистрации и не должна быть единственным bootstrap-способом.
Можно использовать `getUpdates` нового бота до установки webhook через локальный
инструмент с защищённым вводом токена, извлекая только собственный ID, без вывода
токена и личных сообщений. Не отключайте webhook чужого/рабочего бота ради этого.

Затем откройте на своём origin:

- `/tg/setup`: настраивает Telegram, webhook и запускает Ticker;
- `/tg/status`: проверяет состояние.

Webhook должен указывать на `<свой-origin>/tg/webhook`.
Заголовок Telegram проверяется по секрету, вычисленному из токена.
Отдельный `WEBHOOK_SECRET` в исходной версии не нужен.

Пройдите `/start` → свой баркод → регистрация. Первый зарегистрированный
становится администратором: закрытый доступ должен быть настроен заранее.
Проверьте владение новым private-профилем и отсутствие зависимости от старых имён.

Основной таймер — DO alarm, cron страхует его. `last_tick` обновляется примерно
раз в пять минут. `/tg/status` не полностью пассивен: может запустить Ticker.
Не считайте полученный URL доказательством работы напоминаний — проведите
контролируемую проверку со своим аккаунтом.

## 9. Moodle и ограничения

Два независимых источника:

- Личный iCalendar — календарные дедлайны на сервере. Ссылку с `authtoken`
  отправляют своему боту; она приватна и хранится в D1.
- Unitify Bridge — задания, статусы сдачи, оценки, attendance и картинки
  в своей авторизованной браузерной сессии Moodle.

Проверьте реальную синхронизацию после входа владельца в Moodle.
Без браузера бот читает старый снимок, а не новые оценки.

Сохраняйте политику `extension/lib/sync-policy.mjs`: примерно 30 минут между
сборами, максимум два параллельных запроса, разнесённые начала запросов, редкие
аудиты старых заданий, дневные проверки оценок и привязанные к расписанию проверки
attendance, пауза во время тестов/редактирования, backoff и Retry-After.
Одна ошибка не должна обнулять снимок. Не передавайте пароли/cookies и не добавляйте
изменение Moodle, сдачу работ или проставление attendance.

Точное поведение: [extension/README.md](../extension/README.md).

## 10. Приёмка

- Чистая установка зависимостей, сборка, тесты, dry-run.
- Все миграции новой D1, независимые Worker и Ticker.
- Сайт, карта, статистика, переключение дней и темы; проверка мобильного вида.
- Правильные origin в конфиге, расширении, ссылках и картинках.
- Новый webhook, регистрация владельца, команды и отказ постороннему.
- Фактический запуск таймера и контрольное уведомление.
- Pairing с новым сервером, sync, отзыв доступа, отсутствие утечки к старому серверу.
- Свои оценки/attendance/домашки после настоящего чтения Moodle.
- PWA и офлайн отдельно; реальный телефон проверяется отдельно от эмуляции.
- Нет секретов, старых личных профилей и учебных снимков в публичном пакете.

Локальные тесты исходной версии 27 октября 2026: **79 прошли**.
Это не проверка нового развёртывания, новой модели одного владельца или живой LMS.
После адаптации нужны свои результаты.

## 11. Обновление и резервная копия

Перед обновлением облачной базы получите частный экспорт D1 и проверьте его.
Команду и доступные флаги сверяйте с локальным Wrangler:

```bash
npx wrangler d1 export --help
npx wrangler d1 export DB --remote --output /PRIVATE/PATH/unitify-backup.sql
```

`/PRIVATE/PATH` — заменяемый путь **вне репозитория и public/**.
Экспорт содержит приватные учебные данные и ссылки; не публикуйте его.
Секреты Worker сохраняются отдельно защищённым способом и в SQL-экспорт не входят.
Git хранит код/расписания, но не заменяет резервную копию D1.

При восстановлении сначала импортируйте экспорт в отдельную тестовую D1,
подключите отдельный тестовый Worker и проверьте целостность. Импорт:
`npx wrangler d1 execute DB --remote --file <частный-файл>` — только после
проверки выбранного binding/UUID и схемы назначения. Не применяйте полный
экспорт поверх непустой рабочей базы без отдельного плана.
Резервная D1 не копирует состояние DO, секреты и конфиг; их восстанавливают отдельно.
Тестовое восстановление не должно запускать реальные рассылки или менять
webhook рабочего бота.

Обычное обновление: проверить diff → тесты/сборка → backup → необходимые новые
миграции → dry-run → deploy → реальная проверка. При миграциях данных порядок
уточняется по совместимости версий. Откат кода не откатывает D1 автоматически.
После обновления расширения отдельно обновите его файлы в браузере.

## 12. Диагностика

| Симптом | Что проверить |
|---|---|
| Бот молчит | Токен, webhook, реальный ID, допуск одного владельца во всех модулях |
| Setup успешен, напоминаний нет | Ошибки Ticker/очистки, `last_tick`, активные users, учебные даты и часовой пояс |
| Баркод не найден | Исходный профиль, непустой barcode, `people.json`, свежая сборка |
| Ошибка таблицы/столбца | Все SQL-миграции именно выбранной облачной D1 |
| Код расширения не принимается | Тот ли backend, срок 10 минут, допуск, регистрация и SQL pairing |
| Нет новых оценок | Открыта ли LMS, нужный аккаунт, пауза/интервал/backoff, реальные ошибки |
| Неверный attendance | Дата последнего чтения, расписание, соответствия предметов, неизвестные данные |
| Старый сайт | Успешный deploy, service worker/cache, URL и версия ресурсов |
| Ошибка упаковки | `zip`, современный Node.js, зависимости и права на файлы |
